# Agent operation recovery — W5a

W5a provides host-owned immutable schema-2 publication receipts in the existing Catalog SQL transaction, keyed by document/operation and unique output-set ID. Every member version carries the same manifest hash. Healthy rewrites preserve receipts and the store generation; corrupt-primary recovery rotates the generation, so missing evidence in a restored store cannot prove an operation never committed.

`ProjectWriteClaim` is issued only by an acquired project lock and retains the physical cross-process lock while workers hold it. OperationLog v2 freezes original request, resolved plan, exact staging targets and presentation intent. Revision/attempt CAS rejects stale callbacks and immutable-output changes; events retain the latest 128 revisions. Legacy records remain readable and do not claim authoritative absence.

Real linked native verification uses the locked SDK and actual Catalog/DerivedAsset implementations, without storage or publication stubs. `tst_publication_receipt`, existing `tst_catalogstore`, `tst_operation_control` and `tst_algorithm_output_set` all pass. Coverage includes actual subprocess termination/reacquisition, two-process lock denial, receipt/member transaction rollback, replay without another version, corrupted evidence, store rewrite generations, immutable prepared intent and stale-attempt CAS. The 32 CI Source gates plus selftests pass with QGIS 4.2.3 headers; no baselines increased.

W5b remains required: connect this foundation to the production worker/owner commit path, reconcile a lost post-commit response from SQL evidence, and expose scoped operation/result APIs. Publication must remain closed until that path and its crash tests are verified.


## W5b production orchestration

`CapabilityHost` now routes depth, grouped seismic attributes, constraint IDW and contour execution through `CapabilityRecovery`. App assembly injects the actual non-JSON project write claim. `preparePlan/start` is the product DAG facade: the entire original graph is the parent request identity, frozen normalized nodes/ports/defaults are persisted before children, and legacy child kernels write only inside the parent's private attempt directory. Changed graphs conflict before accepting new children. Legacy synchronous numerical helpers remain internal compatibility paths.

Numeric execution, output copy and bounded SHA verification run on the existing `PaleoTaskService` worker pool. The owner verifies live document/effects, frozen source metadata and target CAS, records `publishing`, commits all members plus one immutable SQL receipt, then records the known commit. Losing the journal write after Catalog commit returns `committed_log_repair_pending` with the original committed fact. Read-only reconciliation can return the proven SQL projection without writing, including when a physical claim is still retained. Missing/corrupt/unavailable evidence or a changed store generation never authorizes recomputation.

Prepare/compute-only/publish are separate linked operations. A source operation supplies the original frozen plan, output contract, parent versions, exact target IDs/expected heads, output-set ID and presentation declaration. Publish from a computed result verifies and copies bytes without numerical evaluation (`computeCount=0`). Both initial and restarted prepared publication run the worker input validator and owner source validator. Native typed seismic retains source identity and uses bounded quick verification. Product adapters can chain worker/validator restorers and presentation handlers; a required missing validator rejects restoration.

Presentation is separate from the data transaction. It uses exact frozen member versions and expected target state, recognizes already applied declarations, leaves unreadable state pending, retries at most three applications and marks later user/operation changes superseded. Retained finished task rows release claims and numerical captures; active workers retain physical ownership until private writes finish.

The scoped APIs provide get/events/resume/cancel/results/read. Event and byte cursors are decimal strings, events retain 128 revisions, result descriptors contain opaque operation/port references and bounded worker reads return base64. Result revalidation rejects changed size before hashing and caps each read loop against concurrent growth. Cross-document/chat references are denied; account plus trusted chat-session hash forms the durable caller scope.

External transfer uses the same journal: POST permission is issued only after durable `running`, job IDs are set once, live requests retain an attempt and write claim, restart/uncertain outcomes cannot automatically resend, and reconciliation queries the original remote job. A direct synchronous response needs request/response hashes and the exact frozen model version. Large full results attach as immutable private artifacts after the remote completion fact, without a Catalog publication claim.

### Cumulative Host and cleanup follow-up

The native operation response has the stable `paleo.operation.v2` contract. The central chat adapter preserves independent execution, commit and presentation facts, request identity and opaque operation/receipt references. A response exceeding its JSON byte budget retains those business facts and reports a separate incomplete transport code. The W1 zero-capacity cache regression verifies committed/presentation-pending results and known-receipt replay through the real Host, central adapter and model encoder.

Modern chat requests decode input only before the trusted Host prepares them; publication no longer requires a missing legacy host-head argument. The Host receives the persisted chat-session identity. Known committed replay remains available when the Catalog is read-only. Replay tickets enforce capacity and expire with the document epoch. Full production runner coverage is included in the cumulative build rather than claimed by the focused harness.

External response proofs are immutable for both direct synchronous completion and accepted jobs. A completed result can retain the original host/write claim through private artifact attachment even after the live document changes. Actual remote facts are stored without publishing into the newly active document.

OperationLog v2 supplies conservative GC roots for exact staging outputs, prepared manifests, private result bytes, parent/expected-head versions and frozen source paths, including compound sidecars. The cleanup scan, preview, validation, metadata deletion and each unlink recheck those roots. Unknown schemas, malformed metadata, changed plan hashes, unsafe paths and excessive journal size refuse cleanup. The shared four-field plan hash is verified by both recovery and retention; new operations cannot add roots during a Catalog purge lease. A real native publication regression removes the committed row from a scan snapshot and verifies that durable operation roots still prevent the file becoming an orphan.

Focused verification after these changes: eight real linked suites, 121 QtTest cases passed with no failures or skips, including the opt-in 10,000-file scale case (`PALEO_CATALOG_SCALE=10000`).
